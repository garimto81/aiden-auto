# User-Friendly Report Protocol (v28.2 Section 16)

> **Core Objective**: 비개발자 사용자가 결과 보고를 한 번에 이해할 수 있도록 친절하고 자세하지만 쉽게 풀어 설명. **요약 아님 — 자세히, 단 쉽게**.

## 사용자 명확화 (2026-05-13)

- 사용자 피드백 1: "결과 보고가 지나치게 긴 문제 발생"
- 잘못된 초기 해석: "30-50줄 hard limit 적용"
- 사용자 정정: "**내용은 자세히 알려줘야 하지만, 비개발자가 이해할수 있게 쉽고 직관적으로**"
- 사용자 정정: "**요약이 아니라 모든것을 친절하고 직관적으로 자세하고 쉽게 설명**"

→ **본 protocol의 핵심**: 길이가 아니라 **이해 가능성**이 hard rule.

## Hard Rule

| 항목 | 규칙 |
|------|------|
| 응답 길이 | **제한 없음**. 필요한 만큼 |
| 첫 줄 결론 | 의무 |
| 비유 | 핵심 개념마다 1개씩, 일상 영역만 |
| 약어 풀이 | 첫 등장 무조건 |
| "왜?" 설명 | 모든 작업·결정마다 |
| 단계별 설명 | 한 단계씩 따라갈 수 있게 |
| 기술 점프 | 금지 |
| 상세 데이터 | 채팅에 함께 표시 |
| A/B/C 옵션 | 금지 — 자율 결정 + 이유 |
| 직업군 도메인 비유 | 금지 — 일상 영역만 (도서관/집/식당/요리) |

## 약어·전문용어 풀이 사전 (자주 쓰는)

본 protocol을 적용할 때 다음 용어들은 **첫 등장 시 풀이 의무**:

| 약어/용어 | 풀이 |
|----------|------|
| PRD | 제품 요구 사항 문서 (=만들 제품의 청사진) |
| SSOT | 단일 정본 규칙 (=한 곳이 진짜 답, 다른 곳은 복사본) |
| HMAC | 메시지 위조 방지 서명 (=내용에 자물쇠 같은 코드 붙이기) |
| SHA256 | 내용 지문 같은 고유 코드 (=같은 내용이면 같은 지문) |
| DLQ | 실패 작업 대기실 (=처음 실패한 작업을 따로 모아둠) |
| advisor-tool | Anthropic 공식 도구 (=똑똑한 모델이 빠른 모델을 도와주는 패턴) |
| Stop hook | 작업 끝날 때 자동 실행되는 작은 스크립트 |
| statusline | 화면 상태 표시줄 (=폴더/모델/사용량 표시되는 줄) |
| harness | 외부 도구 묶음 (=우리가 참조하는 다른 시스템들) |
| migration | 옛 데이터를 새 형식으로 옮기기 (=이사 가는 것) |
| backward compat | 옛날 버전과 호환 (=옛날 방식도 작동) |
| schema_version | 데이터 양식 버전 (=양식 종이의 발행년도) |
| Index Router | 안내데스크 (=어디로 갈지 알려주는 역할) |
| chapter | 책의 한 장 (=주제별로 묶은 reference 파일) |
| Phase | 작업 단계 (=한 챕터 안의 단계) |
| Circuit Breaker | 무한 반복 차단기 (=같은 실수 N번 시 자동 멈춤) |
| pdca-iterator | 자동 반복 일꾼 (=목표 미달 시 자동 재시도) |
| Multi-Session | 동시 여러 세션 (=여러 작업 창 동시 진행) |
| Agent View | CC가 보여주는 세션 목록 화면 |
| events.jsonl | 이벤트 기록 파일 (=일지처럼 한 줄씩 추가) |
| Perfect Output Gate | 완벽 검수대 (=Phase 4 진입 전 7항목 자동 검사) |
| E2E QA | 끝에서 끝까지 검증 (=실제 사용 흐름 그대로 테스트) |
| LOGIC_DATA / VISUAL_INTERACTION | 세션 분류 (=논리/데이터 작업 / 화면 보이는 작업) |

(추가 용어 등장 시 본 사전에 등록 + reporter가 자동 참조)

## BEFORE / AFTER 예시 (3가지)

### 예시 1 — Statusline 정정 보고

**BEFORE (전문가용, 비개발자에겐 어려움)**:
```
statusline_compose.py 삭제 + external-harness-registry.md에 hud/* 등록 + plugin.json hooks 32→31. SSOT drift=0 확인.
```

**AFTER (친절·자세·쉬움)**:
```markdown
# Statusline이 이미 있었네요. 제가 착각해서 만들었던 파일 1개만 지우면 됩니다.

## 왜 이런 상황이 됐나요?

쉽게 비유하자면, 음식점에 들어가서 메뉴판이 이미 테이블 위에 놓여 있는데, 제가 "메뉴판이 필요하시죠?" 하면서 똑같은 메뉴판을 하나 더 만들어서 옆에 두려고 했던 거예요.

사용자분이 화면에서 보고 계셨던 4줄짜리 statusline(=화면 하단에 표시되는 상태 표시줄) — 그게 이미 aiden-auto의 statusline이었습니다. 그런데 제가 그걸 모르고 자체 statusline을 또 만들었던 거죠.

## "statusline"이 뭔가요?

Claude Code를 켜면 화면 아래쪽에 작은 정보 줄이 보여요. 거기에 "지금 어떤 폴더 작업 중이고, 어느 모델 쓰고 있고, 얼마나 사용했는지" 같은 정보가 떠 있죠. 그게 statusline이에요. 자동차 계기판 같은 거예요.

지금 사용자분이 보고 계신 4줄:
1. 첫 줄 — 폴더 위치 + Git 상태 + 사용 중인 모델
2. 두 번째 줄 — Claude Opus 모델 사용량 (입력/출력/캐시/비용)
3. 세 번째 줄 — Claude Sonnet 모델 사용량
4. 네 번째 줄 — Claude Haiku 모델 사용량

## 무엇을 정정하나요? — 단계별 설명

### 1단계. 잘못 만든 파일 삭제

제가 만들었던 `hooks/statusline_compose.py`(=상태 표시줄을 직접 만들려고 했던 Python 스크립트)를 두 곳에서 지웁니다:

- 프로젝트 폴더
- 마켓플레이스 저장소

**왜 두 곳?** aiden-auto는 SSOT(=단일 정본 규칙, 한 곳이 진짜 답이라는 규칙)를 따라야 해서 두 미러(=복사본)가 항상 똑같아야 해요. 한 쪽만 지우면 규칙 위반.

### 2단계. 호스트 도구를 "참조 등록"

호스트의 4줄 statusline 도구 3개를 aiden-auto의 공식 추적 대상으로 등록합니다.

**왜 등록만?** aiden-auto의 5가지 원칙 중 첫째가 "외부 도구는 그대로 두고, 참조만"이에요. 우리 폴더로 복사하면 원본이 바뀌어도 우리는 옛날 버전 쓰게 됩니다.

### 3단계. plugin.json 숫자 정정

components.hooks를 32에서 31로 줄입니다.

**왜?** 1개 파일이 줄어들었으니 숫자도 맞춰야 audit(=자동 검사)이 빨간불 안 떠요.

### 4단계. 두 미러 다시 동기화

위 변경사항을 마켓플레이스 저장소에도 반영하고 SHA256 해시값이 일치하는지 확인.

## 결과

- 잘못 만든 파일 1개 두 곳에서 삭제 완료
- 호스트 도구 3개 등록 완료
- plugin.json 숫자 정합
- SSOT drift=0 (=완벽 일치)

## 사용자가 보는 변화는?

**없어요**. 4줄 statusline 그대로 유지됩니다.

## 왜 이게 중요한가요?

1. **원칙 복구**: 5원칙 중 첫째 위반 상태였어요. 이걸 고쳐야 다른 작업도 안 망가져요.
2. **자동 업데이트 추적**: 호스트 도구가 바뀌면 우리도 알아채야 해요. 등록 안 돼 있으면 모름.
3. **숫자 정합**: 매일 도는 검사에서 알람 안 뜸.
```

```markdown
## 왜 이게 필요한가요?

비유로 설명할게요. 식당에서 셰프가 요리한 결과를 손님에게 전달하는 두 가지 방식이 있어요.

**방식 A**: "오늘은 카르파초 12g, 트러플 오일 3ml, 파슬리 칩 5개로 구성된 안티파스토를 준비했습니다."
**방식 B**: "얇게 썬 소고기 위에 향이 좋은 기름과 바삭한 허브 칩을 얹은 전채 요리를 만들었어요. 처음 드시는 분도 쉽게 즐길 수 있어요."

사용자분이 "방식 B처럼 자세하지만 쉽게 설명해 줘"라고 하셔서, 모든 결과 보고를 자동으로 방식 B로 변환해 주는 자동 일꾼을 만들었어요.

## "agent"가 뭔가요?

aiden-auto에서 agent는 특정 역할을 맡은 자동 일꾼이에요. 예를 들어 "executor"는 실제 코드를 작성하는 일꾼, "architect"는 설계를 검토하는 일꾼. 이번에 만든 user-friendly-reporter는 "보고서를 친절하게 풀어 설명하는" 일꾼이에요.

## 무엇을 만들었나요?

### 1단계. user-friendly-reporter.md 작성

agents/core/ 폴더 안에 새 파일을 만들었어요. 이 파일에는 reporter의 역할, 규칙, 변환 절차가 적혀 있어요.

**왜 core/ 폴더?** aiden-auto는 agent를 6가지 카테고리로 나눠 정리해요 (core / creative / domain / iteration / meta / verification). reporter는 모든 작업에 공통으로 쓰여서 "기본 (core)" 카테고리에 넣었어요.

### 2단계. SKILL.md 표시 추가

aiden-auto의 진입점 파일(=SKILL.md)에 "이 plugin은 user-friendly 보고 스타일을 사용한다"는 표시를 추가했어요.

**왜?** plugin 메타 정보로 외부에서도 알 수 있게.

## 결과

- 새 agent 1개 생성 (user-friendly-reporter)
- 새 reference 1개 생성 (사양 문서)
- SKILL.md 표시 추가
- 모든 Phase 4 close 결과가 자동으로 reporter 통과

## 사용자가 보는 변화는?

**앞으로 모든 결과 보고가 친절하게 풀어진 형태로 출력됩니다.** 약어는 풀이되고, 비유로 설명되고, 단계별로 흐름을 따라갈 수 있어요.
```

```markdown
aiden-auto는 매일 두 가지 자동 검사를 돌려서 건강 상태를 확인해요. 사람 몸으로 비유하면 매일 체온 재고 혈압 재는 거랑 비슷해요.

**SSOT(=단일 정본 규칙)**가 뭐냐면, aiden-auto는 똑같은 파일을 두 곳에 보관해요:
```
