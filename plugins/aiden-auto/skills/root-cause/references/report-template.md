# Root Cause 보고서 형식

Phase 3 에서 `user-friendly-reporter` 가 따르는 출력 형식. 15세 기준 평이화 +
`user-friendly-reporter` 의 7-gate (비유 / 약어풀이 / A·B·C 금지 / 결과→이유 순서 등)
를 그대로 적용한다.

## 표준 템플릿

```markdown
# TL;DR — 한 줄 결론

(무엇이 진짜 원인이었는지 한 문장. 비전문 용어로.)

## 무슨 일이 있었나

(증상을 일상어로. 무엇이 안 됐고 사용자가 뭘 봤는지 2~3문장.)

## 진짜 원인

(근본 원인을 일상 비유로 설명. **왜** 그게 원인인지 함께.)
(예: "책 색인이 옛날 페이지를 가리켜서 엉뚱한 곳을 펼친 것" 식)

## 어떻게 알아냈나 (근거)

| 확인한 것 | 발견 |
|----------|------|
| (조사한 지점) | (실제 발견 — 추측 아님) |

## 수정 제안 (아직 적용 안 함)

1. (가장 권장하는 수정 — 무엇을, 왜)
2. (대안이 있으면 — 단순 나열 말고 권장도 함께)

> 적용하려면 알려주세요. 지금은 제안만 한 상태입니다.

## 아직 모르는 점 (있을 때만)

(증거가 부족해 단정 못 한 부분. 더 필요한 정보.)

---
> 한 줄 요약: (전체를 한 문장으로)
```

## 형식 원칙

- **결과 → 이유 순서**: TL;DR(결과)을 맨 위에, 근거는 뒤에.
- **비유 우선**: 기술 용어 등장 시 일상 비유 1개 이상. 비유가 어색하면 차라리 평이하게 풀어쓴다 (직업군 도메인 비유 금지).
- **약어 풀이**: 약어 첫 등장 시 풀어쓴다.
- **추측 금지**: "근거" 표에는 실제 확인한 것만. 단정 못 하면 "아직 모르는 점" 으로.
- **수정은 제안만**: "적용함" 이 아니라 "제안". 적용은 사용자 승인 후 별도.
- **50줄 넘는 덩어리는 표/다이어그램으로 분할**.

## 분류별 강조점

| 분류 | "진짜 원인" 에서 강조 |
|------|---------------------|
| 코드버그 | 어느 코드 경로 / 어떤 입력에서 깨지는지 |
| 운영사고 | 언제부터 / 어떤 변경·배포가 방아쇠였는지 |
| framework | 어느 hook·sync·라우팅 단계가 끊겼는지 |
| unknown | 가장 유력한 후보 + 확정에 필요한 정보 |
