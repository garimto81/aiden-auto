# Friendly Explanation Style — /auto 기본 설명 패턴 (v27.1)

> **목적**: 비전문 개발자(바이브 코더)가 Claude의 작업/결정을 이해할 수 있도록 친절한 설명 패턴을 정형화한다.
>
> **로딩 시점**: 항상 (Phase -2 Triage 진입 직후 + 모든 Phase 결과 보고 시)
>
> **핵심 원칙**: 기술 용어를 비유로 풀어내고, 다이어그램을 텍스트보다 우선시한다.

---

## 5대 설명 패턴 (모든 결과 보고에 의무 적용)

### 패턴 1 — 비유 우선 (Analogy First)

기술 개념을 일상 비유로 먼저 설명한 후 기술 용어를 부가.

```
❌ 금지:
"NTFS의 Alternate Data Streams는 ":" 구분자를 사용한다."

✅ 권장:
"Windows는 파일 이름의 ":" 을 특별하게 봅니다.
 비유: 책 표지의 메모 구분자 같은 역할.
 → ":" 가 들어간 파일명을 "메모를 만들라는 명령"으로
   잘못 해석해서 거부합니다.
 (기술 용어로는 NTFS Alternate Data Streams)"
```

### 패턴 2 — 다이어그램 우선 (Diagram First)

복잡한 흐름/구조는 ASCII 다이어그램이 텍스트보다 먼저.

```
❌ 금지: 5줄 이상의 텍스트로 흐름 설명

✅ 권장:
   [입력]
      │
      ▼
   ┌─────────┐
   │ 처리 1   │
   └────┬────┘
        ▼
   [결과]

   (1줄 캡션으로 보조)
```

### 패턴 3 — 비교 표 (Comparison Table)

여러 옵션/시도가 있으면 표로 비교 (단, 사용자에게 결정 떠넘기는 표는 금지).

```
✅ 권장 (Claude의 결정 비교/실패 사유 정리):
| 시도 | 결과 | 이유 |
|------|:----:|------|
| Plan A (로컬 git)        | ❌ | NTFS 경로 차단 |
| Plan B (gh CLI)          | ❌ | conflict 차단 |
| Plan C (REST API merge)  | ❌ | 같은 알고리즘 |
| Plan D (server merges)   | ❌ | 같은 알고리즘 |
| Plan E (Contents API)    | ✅ | 알고리즘 우회 |

❌ 금지 (사용자 결정 강요):
| 옵션 | 추천 |
|------|------|
| A안 | ⭐⭐⭐ |
| B안 | ⭐⭐ |
| 어느 것을 선택하시겠습니까? |
```

### 패턴 4 — 단계적 빌드업 (Progressive Build)

복잡한 개념은 4단계로 점진 설명: 개념 → 비유 → 적용 → 종합.

```
1. 개념: "3-way merge 알고리즘"
   ↓
2. 비유: "두 사람이 같은 책을 따로 편집하면..."
   ↓
3. 적용: "main과 v27.0이 같은 파일을 수정 → conflict"
   ↓
4. 종합: "이래서 Plan B,C,D 모두 같은 이유로 실패"
```

### 패턴 5 — 한 줄 요약 마무리 (One-Line Summary)

긴 설명 끝에는 항상 표 형식의 한 줄 요약.

```
✅ 권장 마무리:
| 질문 | 한 줄 답 |
|------|---------|
| 왜 발생? | Linux에서 절대경로로 commit |
| 왜 실패? | 모두 같은 알고리즘 사용 |
| 왜 성공? | 알고리즘 자체 우회 |
```

## 기술 용어 → 비유 매핑 사전

자주 등장하는 기술 용어를 비유로 풀 때 일관성 유지.

| 기술 용어 | 권장 비유 |
|----------|----------|
| Index DB | 도서관 카탈로그 |
| Reference 파일 | 책의 chapter |
| Progressive Disclosure | 필요한 chapter만 펼침 |
| 3-way merge | 두 사람이 같은 책 따로 편집 |
| Conflict | 편집장의 판단 필요 (자동 합치기 불가) |
| Branch | 별책 (원본은 그대로 두고 별도 작업본) |
| Commit | 책의 한 페이지 변경 기록 |
| Cherry-pick | 한 commit만 다른 책으로 옮기기 |
| Rebase | 책의 시작점을 옮기고 페이지 다시 쓰기 |
| Merge | 두 책을 하나로 합치기 |
| PR | 변경 제안 (편집장 검토 요청) |
| Force push | 기존 페이지를 강제 덮어쓰기 (위험) |
| API | 서비스에 명령을 보내는 표준 통신 |
| Hook | 특정 사건이 일어나면 자동 발동하는 트리거 |
| Cache | 자주 쓰는 정보를 가까이 보관 |
| Schema | 양식의 빈칸 규칙 |
| Endpoint | 서비스의 특정 기능 입구 |
| Token | 신분증 |
| OAuth | 회원증으로 다른 서비스 접근 권한 부여 |
| 3-Tier 라우팅 | 작업 복잡도에 따라 3단 자동 선택 |
| Iron Law | 절대 어겨선 안 되는 규칙 |
| Circuit Breaker | 자동차의 속도 제한기 (안전장치) |
| Worktree | 같은 책의 별도 사본 (격리 작업) |

## 적용 예시 — Plan A~D 실패 분석 보고 (실제 사용 사례)

이 reference의 모든 패턴이 사용된 모범 답변:

1. **패턴 1 (비유)**: "NTFS의 `:`는 책 표지의 메모 구분자"
2. **패턴 2 (다이어그램)**: 3개 ASCII 흐름도
3. **패턴 3 (비교 표)**: Plan A/B/C/D/E 비교 표
4. **패턴 4 (빌드업)**: 개념(3-way merge) → 비유(편집자 둘) → 적용(main vs v27) → 종합(왜 다 실패했나)
5. **패턴 5 (한 줄 요약)**: 마무리 표 3행

## 금지 사항

| 금지 행동 | 이유 |
|----------|------|
| 비유 없이 기술 용어 나열 | 비전문가 이해 불가 |
| 다이어그램 없이 5줄+ 텍스트 흐름 설명 | 시각화 부재 시 인지 부담 |
| 결정 옵션 4지선다 표 (사용자 떠넘기기) | `feedback_propose_then_execute` 위반 |
| 영문 기술 용어 단독 사용 (예: "force push") | 첫 등장 시 한글 비유 필수 |
| Mermaid 코드 블록 (터미널 응답) | 렌더링 불가 — ASCII만 |

## How to Apply (Claude 행동 룰)

1. **모든 Phase 결과 보고** 시 본 reference의 5대 패턴 의무 적용
2. **새 기술 용어 등장** 시 위 매핑 사전 확인 → 비유 사용
3. **단순 read 응답**도 가능하면 비유/다이어그램 활용
4. **금지 사항 위반 감지** 시 자체 critic하여 즉시 재작성
